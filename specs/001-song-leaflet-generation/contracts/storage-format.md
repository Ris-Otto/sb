# Contract: Storage — SQLite Index + On-Disk Content

This fixes the storage layer's observable behavior: a SQLite index (authoritative for identity
and location, per the 2026-09-11 clarification and FR-018–FR-023) plus the on-disk content files
it points at (per `sb/specification.md` §2.5 and research.md §9, §12, §13). Config (`config.yml`)
was removed 2026-09-26 and is out of scope — see spec.md's 2026-09-26 Clarification.

## SQLite index schema

```sql
CREATE TABLE documents (
    id       INTEGER PRIMARY KEY,
    path     TEXT NOT NULL UNIQUE,
    filename TEXT NOT NULL
);

CREATE TABLE chapters (
    id          INTEGER PRIMARY KEY,
    name        TEXT NOT NULL,
    document_id INTEGER NOT NULL REFERENCES documents(id),
    UNIQUE (document_id, name)
);

CREATE TABLE songs (
    id                   INTEGER PRIMARY KEY,
    name                 TEXT NOT NULL,
    singing_order_number INTEGER NOT NULL,
    chapter_id           INTEGER NOT NULL REFERENCES chapters(id)
);
```

Only `documents` carries a `path`; `chapters`/`songs` locations are always computed (see below).

## On-disk content layout (located via the index, not scanned for)

```text
<documents.path>/                  # arbitrary, user-chosen — from `documents create --path`
├── <documents.filename>.tex       # written immediately by `documents create` (title/subtitle substituted, empty content); overwritten by `documents build` (full content, same title/subtitle re-substituted); renamed alongside `documents.filename` by `documents rename`. Named after --name, not a fixed main.tex. The ONLY per-document file — no document.yml (see below).
└── Chapters/                      # created empty by `documents create`
    └── <chapters.name>/
        ├── chapter.tex            # \chapter*{<title-or-name>} + this chapter's own songs, \input'd from <documents.filename>.tex — generated by `documents build`; absent until first build, and absent (never written) for a chapter with zero songs
        └── <songs.name>.yml       # title, writer?, melody?, number, text lines, score? — source of truth incl. the singing-order number (see below)
```

## Invariants

- A `documents` row with no matching `chapters` rows (or only chapters with no `songs` rows) is
  valid and represents a `Document` with zero chapters/songs (FR-013) — not an error condition.
- A `chapters` row is never created except with a `document_id` referencing an existing
  `documents` row (FR-014/FR-020) — the store never creates one otherwise.
- A `songs` row is never created except with a `chapter_id` referencing an existing `chapters`
  row (FR-015/FR-021).
- `chapter.tex` is a **generated artifact**: `documents build` overwrites it each time it runs; it
  is never a hand-edited input the store must preserve across a rebuild. `<documents.filename>.tex`
  is written at `create` time and overwritten at every `build`, but unlike `chapter.tex` it is
  also **read** (its title/subtitle are parsed back out on every `list`/`find`/`build`) — see
  below.
- A document has **no metadata file of its own** (no `document.yml`, per spec.md's 2026-09-26
  Clarification) — `<documents.filename>.tex` is the sole persisted file, and
  `Document.Title`/`Subtitle` are always recovered by parsing it
  (`DocumentTemplate.ParseTitleAndSubtitle`), never from a separate store. `Document` has no
  `Format` field at all — `--format` is supplied per `documents build` invocation only (see
  `cli-commands.md`), never persisted.
- The `.tex` file's name always matches `documents.filename` (a further 2026-09-26
  Clarification): `documents rename` renames it in the same operation that updates
  `documents.filename`, so the two never drift.
- `songs.singing_order_number` MUST be unique among all songs whose `chapter_id` joins (via
  `chapters.document_id`) to the same document (FR-016) — checked before every insert/update,
  across the whole document, not just the target chapter.
- Removing a `chapters` row removes every `songs` row referencing it, and the corresponding
  on-disk `Chapters/<name>/` folder and its contents (cascading removal — spec.md Assumptions);
  the store never leaves a `songs` row (or `.yml` file) without a parent `chapters` row.
- The index is authoritative for locating a document/chapter/song (FR-022): stores resolve a
  document/chapter/song's filesystem path from the index, never by scanning the filesystem for
  it.
- Before any operation touches a document/chapter/song's on-disk files, the store MUST verify
  the computed path actually exists; a mismatch (missing/relocated folder or file) MUST be
  reported to the user (FR-023, as a `MismatchReport` — see `data-model.md`) rather than silently
  proceeding, silently repairing the index, or silently trusting stale on-disk state.
- `songs.singing_order_number` is a **mirror** of the song's own `.yml` file's `number` field
  (research.md §12) — written whenever `SongStore` writes the file, used for the fast uniqueness
  query above. If the two ever disagree (e.g. the `.yml` was hand-edited outside SB), that is a
  mismatch to surface to the user (following FR-023's pattern), not silently resolve.

## `<song-name>.yml` schema

```yaml
title: string        # required
writer: string        # optional
melody: string        # optional
number: int           # required — the singing-order number; source of truth (research.md §12)
text:                 # required, at least one line
  - string
score:                # optional
  - string             # score/image filename
```

## Verification approach

Tests exercise `SbIndexDatabase`/`DocumentStore`/`ChapterStore`/`SongStore`/`LocationMismatchDetector`
against a temporary directory and a temporary SQLite file, asserting on:
- the schema/constraints above (rejected vs. accepted writes, per `cli-commands.md`),
- the on-disk layout, and
- mismatch detection (create a document, then delete/move its folder out from under the index,
  and confirm a `MismatchReport` is produced rather than a silent failure or silent fix-up),

rather than asserting on exact YAML byte-for-byte formatting (so `YamlDotNet` serialization-style
changes don't require rewriting unrelated tests, per Constitution Principle IV).
